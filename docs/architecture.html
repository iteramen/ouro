ouro architecture

The map: what exists, where it lives, and which layer owns it. contract.md is the protocol, binding.md what a repository declares, rationale.md the reasons, and the README the way in. Every path in the page's prose and tables is a code span the docs-freshness gate resolves against the tree, so a path that stops existing fails a pull request.

Layers

Five layers, one direction of dependency: a caller invokes the driver, the driver calls the node adapter and the scripts, and everything reads and writes the protocol, which is state in the repository and its tracker. The binding feeds the driver, the gates and the installer. The hooks guard interactive shell calls; Codex nodes use their own constrained bridge. Both transports run the same protocol.

Triage

python3 bin/ouro triage N asks the TRIAGE node for a verdict, with the issue, its comments, the anchor gate's answer and contract sections in the brief. Before publishing a PROMOTE or CHECKPOINT, the driver checks the proposed body, labels and exact planned **Triage** comment through the shared shape gate. Mechanical refusal names the gate finding in one NEEDS-RULING verdict, returns exit 3 and never adds agent-ready. On an admitted promotion the missing Size:, Flow: and Doc impact on close: lines are written, the comment is posted and the labels move (a missing area or type label the node names joins the verdict's move). Five verdicts: PROMOTE, NEEDS-RULING, CHECKPOINT, SPLIT for an L, STALE. The body is read again before writes; the separate GitHub updates can still race. A Deliverable clause naming a file the repository no longer has is stale, not a question: the issue is graded by the clauses that remain and the comment says the clause is not delivered. Code: triage and shape_findings in bin/ouro/triage.py, bin/ouro/prompts/triage.md.

The nodes

Five judgment nodes, all through one function, run_node in bin/ouro/node.py: a prompt on stdin, structured final output, declared capabilities and a timeout. Developer configuration selects the worker transport; Codex uses an isolated file bridge with native shell tools disabled. What no node is granted is in the README's "Under the hood". The model per role follows the developer runtime binding and the repository Claude defaults; a stub mode, selected by OURO_NODE_STUB, returns canned answers for the driver suite.

A brief is a template under bin/ouro/prompts/ with slots the driver fills, such as the issue body and its spec comments, the anchors' current lines, the binding's relevant keys, the diff or the record, and the contract sections the node needs, pasted from docs/contract.md by bin/ouro/briefs.py. The REVIEW brief embeds bin/ouro/prompts/REVIEWER-PROMPT.md.

Gates, CI and hooks

Gates are the binding's [[gate]] entries, each a verify command with the keys binding.md defines. python3 bin/ouro-binding.py get gate prints the plugin's own, and gates '*' the ones every issue selects: fixture suites under tests/, selftests, the docs, changelog and command-block gates, the token scan and the release checks.

CI is the one gate run in every class with a pull request: the consumer's workflow, from templates/ci.yml, calls actions/gates/action.yml, which reads the binding and runs every gate, or, with its select-by-paths input on, the ones whose paths the diff touches; actions/docs-freshness/action.yml runs the docs gate. The driver watches those runs and merges at the head they gated. A gate whose ci only prints a notice is another workflow's run and stays with the checks; one whose ci prints a text starting with skip is the driver's to run locally.

Hooks are Claude Code PreToolUse guards registered by hooks/hooks.json on Bash and PowerShell calls: the private-token check (bin/forbidden-tokens.py), hooks/guard-delete.py, hooks/guard-stash-kill.py, hooks/guard-discard.py and hooks/guard-commit.py, each with its own fixture suite under tests/hooks/. They refuse a call whose shape breaks a rule a session could otherwise execute; hooks/README.md is the table. A harness with no hook layer runs without them, which is why nothing in the protocol depends on one.

Placing an idea

An idea or architecture issue is graded against this map. The questions that decide whether it belongs in the plugin, and where:

  • Which layer? A sequence or a transition is driver code with a suite row. A judgment is a sentence in a node's brief. A repository fact, a policy or a path is a binding key, read through the binding reader. A rule a check can read is a gate. A rule with a command shape is a hook. Something that must survive a harness change is protocol: repository state with a writer, a reader and a check.
  • Does it name a repository? The rule in the repository's CLAUDE.md: nothing under skills/ or agents/ names a repository, a path in one, a bot id, a workflow file or a script; that belongs in the consumer's binding.
  • What check fails without it? CLAUDE.md's rule: a rule survives only with a check that fails without it, and a release adds no net lines across skills/, docs/, hooks/, bin/ and tests/.
  • Who can observe it? A reviewer, a gate or a person must be able to see the thing the idea protects, or it is not a mechanism, whatever it looks like.
  • Does it change what a consumer pins? CLAUDE.md's version-bump rule lists what takes a CHANGELOG.md entry under ## [UNRELEASED] and a bump at the tag.
